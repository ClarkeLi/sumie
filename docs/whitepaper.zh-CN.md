## 0. 十分钟导读（给小白）

### 0.1 这个项目在做什么？

想象一个“你画我猜”的游戏：每一轮，一个人要在画布上画出题目，其他人猜。有时候你想把手边的一张漂亮插画画上去，可是回合只有一两分钟，手画根本来不及。

**Sumie 做的事**：你把那张插画“粘贴”到一个网页里，点一下按钮，它就自己把这张图**一笔一笔画**到游戏画布上——而且画的过程、笔迹的粗细、速度的快慢，都和一个手拿数位板的玩家很像，并且保证在回合结束前画完。

### 0.2 为什么不直接“控制鼠标”？

最容易想到的办法是：写个程序，让电脑自己移动鼠标指针、按下左键去拖。这相当于**请一个机器人替你握着鼠标**。它有三个麻烦：

1. **要权限。** 操作系统（比如 macOS）会很警惕“有程序在偷偷控制我的鼠标”，要求你在设置里一次次手动授权。
2. **不稳定。** 鼠标指针的位置受窗口位置、屏幕缩放、你自己有没有碰一下鼠标影响，今天画得好，明天换个窗口大小就歪了。
3. **一眼假。** 机器人移动鼠标是匀速的、粗细一样、折线僵硬，真人则快慢不均，笔压有轻有重。

**Sumie 的办法**：不碰鼠标，而是在游戏里装一个**插件**（可以理解为给游戏加的一个小“接待窗口”），让程序**直接跟游戏说话**：“请在这几个坐标之间画一条线，颜色是这个，粗细是那个。”游戏自己把线画出来，就像你亲手画的一样——也会自动进入游戏自己的“撤销”和“联机同步”流程。

### 0.3 一幅画是怎么“变成”笔画的？

用画画的步骤来类比，Sumie 的流程是：

| 人怎么画 | Sumie 对应的步骤 |
|---|---|
| 先看清楚这张图画了什么、哪里是人物、哪里是背景 | **感知**：抠出主体、提取线稿、找出主要颜色 |
| 在心里打草稿：先勾轮廓，再上色，最后画细节 | **规划**：决定画哪些线、涂哪些色块、先后顺序 |
| 一笔一笔落下，有轻有重、有快有慢 | **人体模型**：给每一笔安排压力、时长和停顿 |
| 看一眼时间，快没时间了就画快点 | **时间预算**：边画边算，必要时加速或少画几笔 |
| 把笔放到画布上 | **插件**：把笔画交给游戏 |

### 0.4 三个关键概念

**① 压感。** 数位板（手绘板）能感知你按得多用力。按得轻，线就细；按得重，线就粗。游戏支持这个功能，所以不同玩家的画，线条粗细各有不同。Sumie 会为每一笔“编”一个合理的力度，并且预先算好游戏最终会把这一笔记成多粗。

**② 图层。** 想象几张透明的塑料片叠在一起：最下面一张涂颜色，最上面一张画黑色轮廓线。你随便涂颜色，也不会把线盖住。游戏只提供了 3 张“塑料片”，Sumie 的插件再把每一张细分成 3 个“区间”，凑出 **9 个虚拟图层**，别的玩家看到的叠放顺序也一样。

**③ 油漆桶。** 画图软件里点一下就把一块封闭区域涂满的工具。它的毛病是：区域边界只要有一个小缺口，颜色就会“流”到整张画布上。Sumie 在电脑里先**模拟**游戏的油漆桶，发现会漏就先补线，再让游戏真正去倒——这样不会翻车。

### 0.5 项目由哪几部分组成？

- **插件**（装在游戏里）：负责和游戏对话。
- **绘制服务**（一个在你电脑上运行的 Python 程序）：负责“动脑”——看图、规划、模拟。
- **网页工作台**（一张网页）：负责和你交互——粘贴图片、预览、点开始。

三者都只在你自己的电脑内部通信（地址 `127.0.0.1`），不连外网，不上传你的图片。

> 到这里，不想了解细节的读者就可以停了。想知道“为什么这样设计”“具体怎么做”的，请继续往下读。

## 1. 全景：按下“开始绘制”之后发生的事

### 1.1 架构图

<img src="../assets/architecture.zh.png" alt="架构图（中文）">

<img src="../assets/architecture.en.png" alt="Architecture (English)">

系统由**两个进程和一个网页**组成：

| 部分 | 运行位置 | 职责 |
|---|---|---|
| 插件 `DrawGuessBridge.dll` | 游戏进程内（BepInEx 6，Unity Mono） | 在 `127.0.0.1:8765` 提供 HTTP / WebSocket 接口；把请求搬到 Unity 主线程；把笔画变成游戏元素；提供虚拟手绘笔和虚拟图层；按配置启动 / 停止 Python 服务 |
| 绘制服务 `studio_server.py` | 本机 Python 子进程，`127.0.0.1:8770` | 单 worker 作业队列；读图、线稿、分割、规划、预览、指标；逐笔执行并回报进度 |
| 网页工作台 `ui.html` | 由插件在 `8765` 提供，自包含，不依赖任何外部 CDN | 粘贴 / 拖入图片，选风格与参数，预览，绘制，撤销 / 重做 / 导出 / 恢复，显示实时词与倒计时 |

**一条设计原则贯穿全局**：*几何和审美决策全部在 Python 里*（改起来快、容易写测试），*C# 只做一件事——把请求安全地搬到 Unity 主线程并落成游戏元素*。这样游戏更新、画风迭代互不拖累。

### 1.2 十二个步骤

当你在网页里粘贴一张图并点“开始绘制”：

1. **网页** 把图片（以及你选的风格、秒数、选区）打包，POST 给 `8770` 的 `POST /jobs`。
2. **作业队列** 收下任务，分配一个编号（比如 `20261104-180000-ab12cd`），在 `.cache/studio/jobs/<编号>/` 建文件夹，存下原图。
3. **读取回合时间**：绘制服务问插件（`GET /api/v1/round`）“这一回合还剩多少秒”。Sketchbook（单人草图本）没有计时器，就用你手动填的秒数。
4. **感知**：读图并缩放 → 分割出主体 → 提取线稿 → 提取调色板。
5. **规划**：产生一个**操作列表**（`line` 线 / `disc` 圆点 / `fill` 填充多边形），每个操作带坐标、颜色、粗细、图层、所属阶段。
6. **人体模型** 给操作加上节奏：每笔多长时间、压力曲线、笔间停顿；并在离线的“油漆桶模型”里预演倒桶，补口防漏。
7. **按时间裁剪**：算出总用时，超过截止时间就从清单**末尾**（最不重要的细节）开始删。
8. **渲染预览** PNG，并计算数值指标（覆盖率、颜色误差、预计用时）。网页显示出来，你可以检查。
9. 你点“开始绘制”：执行器**复用刚才的计划**（不用重新规划）。
10. **执行**：对每一笔，执行器先检查“离截止时间还有多久”，据此决定这一笔画多快，然后向 `8765` 发送请求（整笔直发，或通过“虚拟手绘笔”逐帧回放）。
11. **插件** 把请求放进队列，在 Unity 主线程的下一帧取出，构造游戏自己的“线条信息”，交给游戏创建线条。
12. **游戏** 把线条加入画布，同时记入撤销栈，并同步给房间里的其他玩家。进度一路回报给网页。

### 1.3 为什么要拆成三部分？

- **游戏里只能装 C#（.NET）插件**，而图像处理的生态（OpenCV、PyTorch、ONNX）在 Python 里。拆开后各用所长。
- 把耗时的规划放进**独立进程**，就不会卡住游戏的画面。
- 网页由插件直接提供，用户不需要装任何额外软件，浏览器打开即用。

## 2. 游戏集成层：插件怎样把一笔“交给游戏”

### 2.1 背景知识：BepInEx 与插件

Unity 游戏本身是编译好的程序。**BepInEx** 是一个开源的“插件加载器”：它在游戏启动时，先于游戏代码把自己加载进去，然后去 `BepInEx/plugins/` 文件夹里找 `.dll` 文件，把里面标注了 `[BepInPlugin]` 的类实例化。这样我们的代码就**运行在游戏进程里**，可以直接调用游戏内部的类和函数（前提是游戏用的是 **Mono** 运行时；IL2CPP 版本会把代码编译成原生码，BepInEx 6 的 Mono 加载器就无能为力——所以安装器会拒绝 IL2CPP 版本）。

插件的入口很短（简化自 `Plugin.cs`）：

```csharp
[BepInPlugin("com.clarke.drawguess.bridge", "Draw & Guess Bridge", "1.0.0")]
public sealed class BridgePlugin : BaseUnityPlugin
{
    void Awake()   { /* 读配置；启动 HTTP 服务；按需启动 Python 绘制服务 */ }
    void Update()  { _server.Pump(); }       // 每一帧：处理排队中的动作
    void OnDestroy(){ /* 关闭服务，停止 Python 子进程 */ }
}
```

**怎么编译？** 插件要引用游戏自己的程序集（`Assembly-CSharp.dll` 等）和 BepInEx 的程序集。仓库**不分发**它们：`tools/install.py` 会在你机器上从游戏目录复制出需要的 DLL 到 `.cache/game-managed`，下载并校验 BepInEx 到 `.cache/bepinex`，再用 `dotnet build`（目标 `netstandard2.1`）编译。这是“不重新分发游戏文件”的实现方式。

### 2.2 为什么需要“主线程调度器”

Unity 有一条铁律：**只有主线程可以碰游戏对象**（创建线条、读取画布……）。而 HTTP 服务器要同时处理很多请求，必须跑在别的线程。

比喻：游戏主线程是一位**只在柜台办事的柜员**，HTTP 线程是**大堂里的引导员**。引导员不能自己进柜台，只能把你的单子（一个 `Action`）放进**收件篮**，柜员每一帧抽空从篮子里取单子来办，办完把结果交还。这个“收件篮”就是 `MainThreadDispatcher`：

```csharp
// 简化自 MainThreadDispatcher.cs
ConcurrentQueue<Action> _queue;
public void Post(Action a) { if (IsMainThread) a(); else _queue.Enqueue(a); }
public void Pump(int max = 256)          // 每帧由 Update() 调用
{
    for (int i = 0; i < max && _queue.TryDequeue(out var a); i++)
        try { a(); } catch (Exception e) { Log.LogError(e); }
}
```

几条细则：

- **每帧最多处理 256 个动作**，避免一帧被塞满导致画面卡顿。
- 普通请求通过 `InvokeJson()` 等待结果，**15 秒超时**返回 HTTP 504。
- 批量笔画是“长操作”，等待上限 `LongOperationTimeoutSeconds`（默认 180 秒）；它在**协程**里执行，每 `StrokesPerFrame`（默认 24）条就 `yield return null` 让出一帧。
- WebSocket 的每条消息也走调度器——**不要**在 WebSocket 的循环里做长任务。

### 2.3 三套坐标，最容易搞错

| 空间 | 范围 | 原点 | 用途 |
|---|---|---|---|
| **归一化画布** | `x, y ∈ [0, 1]` | **左下角**，y **向上** | 接口里的 `points`、计划 JSON |
| 画布世界坐标 | `x ∈ [-8.89, 8.89]`，`y ∈ [-5, 5]` | 画布中心 | 游戏内部、调试 |
| 截图像素 | 例如 1920×1080 | 左上角，y **向下** | 预览、与截图对比 |

换算（`GetCoords`）：

```text
worldX = surface.MinX + nx * surface.Width
worldY = surface.MinY + ny * surface.Height
屏幕像素 y = 画布顶 + (1 - ny) * 画布像素高          # 对截图要翻转
```

**为什么选“y 向上”？** 因为游戏的世界坐标就是 y 向上；在 Python 里统一用游戏的方向，只有“画到图片上”这一步才翻转一次。验证方法：导出 `/api/v1/lines`，头顶描边的 y ≈ 0.92，脚的 y ≈ 0.07。

所有坐标写入时会 `Clamp01`；出现 `NaN` / `Infinity` 直接返回 400。

#### 把一张图“摆”到画布上（`make_transform`）

画布是 16:9（世界 17.78×10），图片比例各异，需要等比缩放并留白：

```text
fit_w = fit_h = 1 - 2*margin                      # margin 默认 0.04
若 图片更宽:  fit_h = fit_w * 画布宽高比 / 图片宽高比
否则:        fit_w = fit_h * 图片宽高比 / 画布宽高比
nx = origin_x + (x / 图片宽) * fit_w
ny = origin_y + (1 - y / 图片高) * fit_h          # 翻转成 y 向上
```

**工作示例**：一张 480×300 的图（宽高比 1.6），画布宽高比 1.778，margin = 0.04。图片比画布窄，所以 `fit_h = 0.92`，`fit_w = 0.92 × 1.6 / 1.778 = 0.828`；`origin_x = (1-0.828)/2 = 0.086`。于是图片中心 (240, 150) 映射到 (0.5, 0.5)，左上角 (0, 0) 映射到 (0.086, 0.96)。

### 2.4 笔宽的换算

游戏里的线宽**恰好等于 `size / 100` 个世界单位**（`size` 是界面里 1–255 的画笔号）。换成像素：

```text
px = size × 画布像素宽 / (100 × 画布世界宽)       # 画布世界宽 = 17.77778
```

1920 像素宽的画布上，1 号笔约 1.08 px，30 号笔约 32 px。预览渲染、网页预览、对比工具**必须用同一个公式**，否则就会出现“预览比实际粗”的问题（项目历史上真出现过，修好后：预览与实际镂空 0.0 %，墨量比 0.95，线宽 5.7 对 5.5 像素）。

**线头与折角**：游戏画出的线**两端是平的、折点是圆的**（只有“高线质量”开启或 `RoundLineJoins=true` 时折点才圆）。想要圆头笔，只能在笔画起点、终点各补一个同色、直径等于线宽的 `disc`。这是写在文档里的结论：`RoundLineJoins` 只修折角，不是“圆头”。

### 2.5 一笔是怎样落到游戏里的

对应 `GameApi.ApplyOneStroke()`：

1. 校验 `CanDraw`（除非请求里 `force=true`）。
2. 坐标：`space=normalized` 直接用；`canvas` / `world` 先换算。
3. 类型归一：`line` 至少 2 点（1 点自动变 `disc`）；`disc` 只留第一个点；`fill` 至少 3 点，并去掉与首点重合的末点。
4. 颜色缺省用当前画笔颜色；大小缺省用当前笔刷。
5. 构造 `LineInformation`：`DrawElementType` 取 0 = 线、1 = 圆点、3 = 填充；`IsNormalized = true`；`AspectRatio`、`ScaleFactorWidth` 取自画布。
6. 调用 `DrawHelpers.SpawnDrawElement`，得到 `DrawableLine` / `DrawableDisc` / 填充。
7. 折点强制圆接头（`RoundLineJoins`）。
8. 加入当前模块的“已创建元素集合”，执行 `OnFinishDrawingCurrent`（对“大逃杀”模式走精简版本，避免每条线都触发机器学习识别）。

**一个游戏的怪癖（实测发现）**：每次填充之后，游戏让这块填充保持“可选中”状态，下一笔或下一次换色会把它**重新染成当前颜色**。正常玩家会切换工具所以不会触发；桥接从不切换工具，于是会出问题。两处对策：插件在每次 `RealFill` 之后调用 `LineFillable.SetLineSelectActive(false)`；执行器在每次倒桶后调用 `tool("Brush")`。

### 2.6 HTTP / WebSocket 接口（核心几个）

| 端点 | 作用 |
|---|---|
| `GET /api/v1/state` | 能否绘制、工具、颜色、笔刷、画布尺寸、图层、元素数 |
| `GET /api/v1/game` | `state` + 回合计时器 + 当前词、上一轮词、词历史 |
| `GET /api/v1/round` | 场景里所有 `Timer`，以及 `recommended.remaining`（剩余秒数） |
| `GET /api/v1/lines?limit=N` | 导出**自己**的笔画（`points` 已归一化） |
| `POST /api/v1/strokes` | 批量画线 / 圆点 / 填充 |
| `POST /api/v1/stroke/pen` | 通过虚拟手绘笔逐帧回放一笔（带压力） |
| `POST /api/v1/fill` | 真正的油漆桶（按种子点），返回新色块面积 |
| `POST /api/v1/undo` `redo` `clear` `submit` `color` `brush` `tool` `layer` | 常规操作 |
| `GET /api/v1/layers` | 虚拟图层能力 |

`POST /api/v1/strokes` 的请求体（最小例子）：

```json
{
  "clear": false,
  "strokes": [
    {"type": "line", "color": "#FF3355", "size": 10, "space": "normalized",
     "points": [[0.10, 0.20], [0.25, 0.80], [0.50, 0.30]]},
    {"type": "disc", "color": "#000000", "size": 8, "points": [[0.5, 0.5]]}
  ]
}
```

响应：`{"applied": 2, "failed": 0, "requested": 2, "errors": []}`。如果在配置里设了 `Token`，请求头要带 `X-Api-Key: <令牌>` 或 `Authorization: Bearer <令牌>`。完整字段见 [`api-reference.md`](api-reference.md)。

## 3. 感知：电脑怎样“看懂”一张插画

目标：从一张位图里得到三样东西——**哪里是主体**、**线稿是什么**、**主要有哪些颜色**。

### 3.1 读图与缩放

按剩余时间在 **480–960 像素**之间自动选最长边：时间短就缩小（规划快），时间长就保留更多细节。不指定时由 `dg_artist.py` 自动决定；Studio 里“最大边长”留空即自动。

### 3.2 主体分割（`anime_seg.py`）

使用 `anime-segmentation` 的 **ISNet** 模型（ONNX 格式，`models/anime-seg/isnetis.onnx`，用 ONNX Runtime 推理），输出一张“哪个像素属于人物”的蒙版。没有模型时回退到 OpenCV 的 **GrabCut**（交互式前景提取算法）。

为什么要抠主体？因为背景的细碎纹理对“画像不像”帮助不大，却会占掉宝贵的笔画预算。

### 3.3 线稿提取（`study_lineart.py` + Anime2Sketch）

线稿决定了“像不像”。流水线：

1. **Anime2Sketch**（一个 U-Net 神经网络，`client/anime2sketch_net.py` 是它的重新实现，可直接加载官方权重 `netG.pth`）把彩图变成干净的黑白线稿。有 CUDA 或 Apple MPS 时约 2 秒，否则用 CPU。没有 torch / 模型时回退经典边缘检测（梯度 / 脊线）。
2. **骨架化**：把粗细不一的线“瘦”成 1 像素宽的中心线（`artist_geometry.py`）。
3. **接线**（`merge_paths`）：骨架在交叉点会断成很多碎片。按“**切线连续性**”把方向相近的碎片接成长线——就像人会一笔画过交叉口，而不是在每个路口抬笔。
4. **断线**：只在真正的转角处断开，单笔长度不超过画幅的 **24 %**（太长的笔画人手画不出来）。
5. **补轮廓**：外轮廓的缺口用主体蒙版的轮廓补上。
6. **分级与取舍**：每条线按“长度 × 墨色深度”打分，分三级——**外轮廓**、**主要内线**（阶段 `sketch`，先画）、**细节线**（阶段 `detail`，最后补）；再用“最近邻”排序（从左上角起笔，下一笔选离当前笔尖最近的起点），减少抬笔距离。

### 3.4 调色板与色块

1. 在 **Lab 颜色空间**做 k-means 聚类，取少量基色（默认由时间决定，一般 3–8 种）。Lab 空间里“数值距离”和“人眼觉得的颜色差别”更接近，所以聚出的颜色更自然。
2. 对**标签图**（每个像素属于哪个基色）做平滑，去掉噪点。
3. 每个色块取外轮廓，简化成**只有少数几个角点的简单多边形**（`fill` 操作）。
   - **自交多边形绝不发送**：游戏会把自交图形三角化成一大块深色，而预览（even-odd 规则）会留空，造成预览和实际不一致。
   - 露出纸面的“洞”不能用多边形盖，这类色块退回粗笔涂抹（`paint_mass`）。

### 3.5 被画框切掉的人物（`frame_cut.py`）

半身像的下边、手臂的截断处在图片边缘是一条**笔直的切口**，如果照抄，一眼就能看出是“照着图抄”的。处理办法：

1. 检测人物与每条图片边相接的区段；
2. 用一条向人物内部弓起、带慢波和微颤的**不规则曲线**替换直边（弓起幅度约为人物大小的 5 %），把人物蒙版裁到这条曲线；
3. 靠近曲线的线稿在**随机位置**收笔，一部分变成越来越短、越来越淡的“消失线”；
4. 沿新边缘不画墨线、不画深色边：色块在一堵“看不见的、起伏的墙”前结束。

数值检查 `tools/frame_check.py`：沿每条被切的边，绘画停在**同一像素位置**的比例，照抄是 0.76–1.0，处理后是 0.2–0.35（> 0.4 视为不合格）。代价：裁掉约 5–8 % 的人物，与原图的 LPIPS 稍差（约 0.005–0.03），这是有意取舍。

## 4. 规划：把图变成有顺序的笔画清单

### 4.1 “操作”（Op）长什么样

规划的输出是一个**确定的**（同样输入 + 同样随机种子 → 同样输出）操作列表，每个操作大致包含：

```text
type     line | disc | fill
points   [[x, y], ...]                 归一化、y 向上
color    #RRGGBB
size     1–35 的画笔号（线宽）
layer    真实图层 或 虚拟图层
phase    sketch / color / shade / detail ...
role     construction / contour / inner / detail / accent / gap_close / shade / fill
alt      倒桶的备用种子点
```

“确定性”很重要：它让预览和绘制能复用同一份计划，也让测试可以比对 JSON。

### 4.2 画什么、按什么顺序（`anime_human` 的顺序）

1. **线稿**：按部位聚类（从上到下），长轮廓在前、短细节在后；每笔两端多出几格（像人收笔时越过交点）；横线习惯左→右，竖线习惯上→下。
2. **平涂（flatting）**：对每个色块，先试“现有线条能不能已经把它围住”——能就直接倒桶或涂；不能就在缺口处补一两笔短线，最后才整圈描边（描边用**该色块自己的颜色**，两头多出几格接在邻居的线上）。
3. **笔刷块与阴影**：用粗笔、较高压力补出。
4. **细节线稿最后画**：眼睛、衣褶、发丝。

**时间分配**（针对 120 秒左右的短局调过）：线稿是骨架，占整局约 **38 %**——其中三分之二先画（轮廓和结构），三分之一留到颜色之后画内部细节；平涂做到约 **88 %** 减去这份细节预留；之后如有剩余时间，继续平涂剩下的色块，而不是拉长停顿。短局里“**完成度比细节重要**”：宁可线稿少、颜色多，也要保证结束时画面是完整的。

### 4.3 为什么“线稿放最后”那条细节线要放在颜色之后

颜色（尤其是大色块）会盖住下面已有的线。所以最终的细节线稿必须在颜色之后画，或者放在**更高的图层**上。这正是虚拟图层要解决的问题（见 5.4）。

## 5. 人体模型：怎样让每一笔都像人画的

`anime_human` 只决定**怎么画**，不改变**画什么**。它由四个独立、各自可测试的模型构成。

### 5.1 压感模型

#### 5.1.1 游戏的压感规则（读源码得到）

- 打开“压感检测”后，画的时候线宽实时随压力变化，**但只有本机看得到**。
- 一笔画完，同步给所有人的 `LineInformation` 里**只有一个 `BrushSize`**（整笔一个粗细）。
- `BrushSize` 的算法：对每一帧压力 `p`（只有 `p > 0.05` 才算“按下”）算 `int(2 + 33 × min(1, p))`，存进一个 **10 格环形缓冲**；一笔结束时，取**第 5 新到第 9 新**的 5 个读数求平均；抬笔前最后 4 帧不计入。

所以真人手绘板玩家留下的是：**笔和笔之间粗细不同，一笔之内一致**。

#### 5.1.2 Sumie 的移植（`motor.py::game_brush_size`，原样节选）

```python
PEN_MIN, PEN_MAX, SMOOTHING, DROP, CUTOFF = 2, 35, 10, 5, 0.05

def game_brush_size(pressures):
    values = [0] * SMOOTHING
    index = consider = 0
    for p in pressures:
        if p > CUTOFF:
            values[index] = int(PEN_MIN + (PEN_MAX - PEN_MIN) * min(1.0, p))
            index = (index + 1) % SMOOTHING
            consider = min(consider + 1, SMOOTHING)
    if consider == 0:
        return None
    if DROP >= consider:
        return int(sum(values[:consider]) / consider)
    total = 0
    for i in range(consider - DROP):
        total += values[(index - DROP - i) % consider]
    return total // (consider - DROP)
```

**工作示例**：一笔的逐帧压力是 12 帧恒定的 `0.5`，则每帧读数 `int(2 + 33×0.5) = 18`，结果 `BrushSize = 18`。若压力恒为 `0.062`（略高于 0.05 的门槛），读数为 `int(2 + 33×0.062) = 4`，结果 4（项目里写的“最细只能存成 3”，对应压力下限 `PRESSURE_FLOOR = 0.052`）。若只有 3 帧压力 0.5 后抬笔，窗口里“第 5 新到第 9 新”的读数不足，会退化成对已有读数求平均，仍是 18。

**反推**：给定想要的 `BrushSize = S`，需要的压力约为 `p ≈ (S − 2) / 33`；再加一点随机抖动，并保证每一帧都 > 0.05（否则游戏会把一笔拆成两笔）。执行器用游戏自己的平滑逻辑反推压力曲线，使最终存下的 `BrushSize` 命中目标（实测整体误差 9——对约 200 笔而言很小）。

#### 5.1.3 两个防“被削头”的细节

- 刚落笔时游戏会晚一两帧才开始记线，起点会被削掉 1–4 格 → 每笔先在起点**按住 70 毫秒**再移动。
- 每一帧压力都必须 `> 0.05`，直到抬笔。

#### 5.1.4 两种落笔方式

- **`direct`**：一笔画完，一次性把整条线连同模型算出的 `size` 发给游戏（`POST /strokes`）。不需要压感，也不需要虚拟笔。
- **`native`**：插件创建一个**虚拟 `Pen` 设备**（Unity 新输入系统里的数位笔），按 `[t_ms, x, y, 压力]` 的采样**逐帧回放**（`POST /stroke/pen`），走游戏**自己的**输入路径：线真的一帧一帧长出来，`LinePressure` 自己算 `BrushSize`、简化点、同步、记录撤销。回放期间不要动鼠标（`Pointer.current` 会变回鼠标，压力归零，这笔提前结束）；游戏在后台时，插件临时设 `backgroundBehavior = IgnoreFocus` 并打开 `runInBackground`，结束后恢复。**连续 3 笔游戏都没接受就自动退回 `direct`。**

`--pen auto`（默认）：游戏里压感打开且插件支持虚拟笔时用 `native`，否则 `direct`。

#### 5.1.5 各类笔画的“手感压力”

不同类型的笔，手的力度不同（`ROLE_PRESSURE`，占传感器量程的比例）：

| 角色 | 压力范围 | 含义 |
|---|---|---|
| construction（构造线） | 0.065–0.11 | 很轻 |
| contour（轮廓） | 0.07–0.17 | 轻到中 |
| inner（内线） | 0.065–0.14 | 轻 |
| detail（细节） | 0.062–0.105 | 最轻 |
| accent（点缀） | 0.18–0.34 | 较重 |
| gap_close（补口） | 0.07–0.13 | 轻 |
| shade（阴影） | 0.062–0.10 | 轻 |
| fill（粗笔涂色） | 0.30–0.55 | 宽扫，压力按笔号反推 |

另外每个“人”有一个整幅画的**习惯系数** `habit = exp(N(0, 0.12))`（今天整体按得偏重还是偏轻），让同一个种子下的整幅画保持一致的“手感”。

### 5.2 节奏模型

#### 5.2.1 数据从哪来

`tools/calibrate_motor.py` 读 Google **Quick, Draw!** 的原始数据（真人涂鸦，带逐点时间戳，约 **8.5 万笔**），拟合出：

- **单笔时长–长度幂律**：`时长 = a × 长度^b × 噪声`，默认 `a = 0.885, b = 0.616`，噪声为对数正态（`σ = 0.62`）。长度是相对于整幅画长边的比例。意思是：笔画越长越费时，但**不是线性的**（长线画得更快）。
- **笔间停顿**：对数正态，`μ = −0.79, σ = 0.72`；并且停顿随“抬笔后移动到下一笔起点的距离”线性变长：`停顿 ≈ 0.44 + 0.5 × 移动距离`。
- **钟形速度剖面**：把一笔分成 20 段，每段的相对速度（起笔慢、中间快、收笔慢）：`[0.63, 0.82, 0.98, 1.08, 1.13, 1.15, 1.15, 1.13, 1.10, 1.07, 1.04, 1.00, 0.96, 0.92, 0.88, 0.84, 0.80, 0.75, 0.70, 0.63]`。
- **曲率–速度幂律**（β = −0.416）：转弯越急、走得越慢。

**只有这些汇总统计随仓库发布**（`client/calibration/quickdraw_motor.json`），原始数据不入库。数据本身不含压力，压力曲线按手写和数位板研究里常见的“上升–平台–衰减”形态建模。

#### 5.2.2 各类笔的时间系数

`ROLE_TIME`：construction 0.8、contour 1.0、inner 0.95、detail 0.85、accent 1.2、gap_close 0.7、shade 1.05、fill 0.75（越小越快）。再除以“熟练度” `skill`（默认 2.3，可调；数字大，画得更快更流畅）。单笔时长被夹在 **0.16–3.6 秒**。

### 5.3 采样：把一笔变成逐帧点

游戏**只有移动超过一定距离才记录一个点**（`MIN_STEP_WORLD = 0.015` 世界单位），并且每帧读一次输入（`--game-fps`，默认 240，`tools/probe_pen.py` 可测出真实值）。`sample_stroke()` 沿路径按“时间 + 速度剖面”生成 `[t, x, y, 压力]`，压力曲线带“上升–平台–衰减”。帧率之所以重要：它决定“第 5–9 新的读数”对应抬笔前多久。

### 5.4 虚拟图层与画笔涂色

#### 5.4.1 问题

油漆桶要求目标区域被**同一图层**的线完全围住。漏一个口，颜色就冲出去，补口的深色边又让画面不干净。真人用图层：线稿一层，颜色在下面一层，随便涂，盖不住线。

#### 5.4.2 游戏的限制与突破口

游戏只有 **3 个排序层**（`SHAPES_1..3`，各带 `_FILL`），运行时不能新增。**但每条线同步时带着 `Layer` 和 `SortingOrder` 两个值，接收方按这两个值摆放。** 插件利用它：把 `SortingOrder` 切成若干**区间**（band），于是

```text
虚拟图层 v  =  (真实图层 v ÷ bands 取整,  区间 v mod bands)
SortingOrder = -28671 + band × 20479 + 计数
```

默认 `bands = 3`，所以 **3 × 3 = 9 个虚拟图层**。规则：**高层永远盖住低层，与画的先后无关**；同一真实图层里，填充（桶）永远在线条之下。因为这两个值会同步给所有玩家，**别人看到的叠放顺序一样，对方不需要装插件**。

为了让一笔“从落下的第一帧就在正确的层上”，插件用 Harmony 补丁在游戏创建线条的那一刻（`DrawableElement.Init`）改写排序层和顺序（`nativePatch`）；为了让相册 / PNG / SVG 导出的顺序正确，导出列表按 `(Layer, 是否填充, SortingOrder)` 排序（`exportSort`）。

#### 5.4.3 角色到图层的映射（`layers.py`，9 层时）

| 层 | 角色 | 内容 |
|---|---|---|
| 0 | sketch | （预留） |
| 1 | flat | 大色块 |
| 2 | flat_top | 小于总面积 2 % 的色块 |
| 3 | shade | 阴影笔触 |
| 4 | light | 颜色点缀 |
| 6 | ink | 线稿、补边 |
| 7 | top | （预留，线稿之上） |

少于 9 层时角色共用层（**最少 5 层**）；少于 5 层或插件没有 `/api/v1/layers`（旧插件、游戏没重启）就**自动回退油漆桶**。

#### 5.4.4 画笔涂色算法（`brush_fill.py`）

目标：像人一样，用粗笔来回扫、小笔沿边收、最小笔点角。它在比桶模型**细一倍**的栅格上工作（笔号 s 就是 s 个像素宽，因为游戏一个碰撞格是 0.02 世界单位，而线宽是 `s/100`）。

1. **可涂范围** = 色块多边形 ∪（线稿 ∪ 之后才画的色块）在 18 格内的部分：笔可以压在线上、压在之后会盖掉它的色块上，但不会涂到白纸，也不会盖住已经画完的色块。
2. **厚的地方**（35 号笔装得下且有余量）：先沿边缘走一圈，再沿长轴来回扫（锯齿连成长笔），行距为笔宽的 **0.86**。
3. **细长的地方**（发丝、边缘）：取中轴线，在分叉处把走向相近的段接起来，每条用刚好够宽的笔（**35 / 22 / 12 / 6 / 3**）一笔画完。
4. **每笔必须新增至少 4 % 的覆盖面积**，否则丢弃；覆盖目标 **93 %**（小色块 85 %），最外圈 1 格不要求（在线稿下面）。
5. 同色色块连着画（尊重“后画的在上”），少换色；第一轮每块都先有颜色，第二轮再收边（收边只在色块自己范围内，免得盖住邻居）。
6. 最后：没有线的色块边缘补一圈深色细边（在 `ink` 层），阴影和点缀笔触裁到“整支笔都落在色块里”的部分，再画细节线稿。

### 5.5 油漆桶的离线漏色模型（`bucket.py`）

游戏的油漆桶（`ShapeFiller` + `CollisionMatrix`）规则被移植成离线模型：

- 把画布按 **0.02 世界单位**划成栅格；
- 每条**折线**在栅格上是一堵墙，两侧半宽 `= 线宽/100 × 0.2`；
- **圆点不挡**；**填充多边形**会加上它的边；
- 游戏会先把每条线简化（`GAME_SIMPLIFY = 0.01` 世界单位），模型也先做同样的简化。

**规划时**，对每个要倒桶的色块先在模型里试倒：

1. 漏了 → 找到“逃逸路径最窄处”补一笔短线；
2. 仍漏 → 整圈描边；
3. 色块被线条切成几块 → 每块各倒一次；
4. 很小或很细的色块不倒桶，用一笔“点画”。

**执行时**：游戏的 `POST /fill` 返回新色块的实际面积；**实际 > 预测 × 1.8 就 `undo`**，用游戏里*真实的*线重新找口、补一笔、重倒（游戏会简化记录的点，偶尔出现模型没见过的口）。倒出面积不到预期 **35 %** 的，先换**备用种子点**（`Op.alt`），都不行就撤销，不留碎点。种子点取“**真实格子里最深的点**”（离墙最远），而不是色块多边形的中心——因为中心点可能落在墙另一侧的小口袋里（历史上踩过的坑：一次倒桶预期 0.0095，实际只有 0.0001）。

实测：约 200 笔，31 次倒桶，**0 次漏色、0 次修复**。

## 6. 时间预算：怎样保证绝不超时

### 6.1 两层预算，别混淆

**第一层：通用笔画预算**（`dg_artist.resolve_budget`）

```text
remaining  ← 来源优先级：/round.recommended.remaining → --time → --default-time(180)
usable     = remaining − max(2, remaining × 0.08)           # 预留 8 %
速率       = 联机 11 单位/秒；离线 Sketchbook 65 单位/秒
上限       = sketch 1600 · anime_flat 2200 · anime_study 900 · impasto 3000 · watercolor 2000
```

**第二层：执行截止时间（绝对时间）**

```text
planning_start = 读图 / 模型推理之前的 time.monotonic()
deadline       = planning_start + usable
```

执行器在**每一笔、每次换色之前**都检查它；规划、清空、切图层的耗时**都不会重置**这个截止时间。所以 `--time 180` 的真正含义是“从开始规划算起 180 秒内画完”，**而不是“规划完再画 180 秒”**。

另外 `pacing.py` 还有一套安全规则：保留 **12 %**（至少 3 秒、至多 20 秒）；测得的请求延迟乘 **1.3** 的边距才可信；回合计时器每 **6 秒**重读一次，截止时间**只会提前、不会推后**；慢速模式最长的批间停顿 1.2 秒；停顿最多压缩到 **40 %**（`SPEED_FLOOR`）。

### 6.2 “自动读回合”时的整局策略（`anime_human`）

- **规划按这局的最长时间**（计时器的 `peak = max(总时长, 已过 + 剩余)`）：180 秒的局，哪怕开画时只剩 120 秒，规划仍是 180 秒的那一幅；规划内容的预算是 `peak − 30 s`。
- **执行必须在“当前剩余 − 30 秒”内完成**（短局最多留 40 %），给玩家留出调整时间。
- **动态压缩**：每笔之前算压缩比

```text
压缩比 = 剩余可用时间 ÷ 后面所有笔的“自然时长”之和       # 下限 0.3（约快 3 倍）
```

同一幅画于是画得更快：压缩的是笔画时长和停顿；原生笔会把每笔的采样时间一起按比例压缩（落笔后的 70 ms 停顿保留）。仍然不够时，**从计划末尾（最不重要的细节线稿）开始少画几笔**。

**实测例**：180 秒规划的 290 个操作，只给 90 秒（截止 79 秒），实际在 79 秒内画完 277 个，全部走原生笔、无失败、倒桶无漏色。

### 6.3 一个常见误解

“时间长了会不会画得更细？”会。时间只会**多不会少**：规划按整局最长时间来，操作数随预算增加（我们实测：同一张图 170 秒预算约 356 个操作，300 秒约 555 个，脸部细节才明显出现）。

## 7. Studio 服务与网页工作台

### 7.1 作业（Job）的生命周期

```text
queued → planning → planned（预览就绪）→ drawing → done
                        └──────────────→ cancelled / failed / interrupted
```

- **单 worker 队列**：一次只规划 / 绘制一个作业，避免两幅画互相抢笔。
- 作业文件夹 `.cache/studio/jobs/<id>/`：`input.png`（原图）、`plan.json`、`preview.png`、阶段图、`progress.json`、`run.log`、`metrics.json`、`job.json`。**刷新网页不会中断作业**——作业本体在 Python 服务里，页面只是在轮询。
- **计划复用**：先预览再绘制时，绘制直接读 `plan.json`（`--plan-in`），不再重新规划。
- **选区**：`--region x,y,w,h`（归一化，y 向上，左下角为原点），只在画布的一块区域里画。
- **导出 / 恢复**：`GET /lines` 导出当前画布为 JSON；`tools/restore_canvas.py` 或页面上的“恢复笔画”回放，用来在重启游戏前保存进度。
- **默认保留画布**：绘制前清空必须手动勾选并确认。

### 7.2 数值指标

| 指标 | 含义 |
|---|---|
| 覆盖率 | 计划覆盖了主体的多少 |
| 外溢 | 画到主体以外的比例 |
| 颜色误差 | 已涂部分与原图的颜色距离 |
| 弯曲比 | 笔画的弯曲程度（是否过于笔直） |
| 预测漏色 | 离线桶模型预测会漏的次数 |
| 笔 / 分钟 | 节奏 |
| 预计用时 | 完成整个计划需要的秒数 |

### 7.3 网页的多语言怎么实现

页面是**一个自包含的 HTML 文件**（无 CDN、无构建步骤），源语言是中文。翻译没有散落在业务代码里，而是用一张**词典 + 自动翻译层**：

1. 词典是一个数组 `I18N_ROWS`，每行 5 列：`[中文原文, English, 日本語, 한국어, Deutsch]`。
2. 含 `{0}` `{1}` 的行是**模式**（例如 `已用 {0}s`），运行时转成正则，匹配后把捕获的片段**递归翻译**再填回模板。
3. 对 `A · B · C` 形式的拼接文字（比如状态栏），按 ` · ` 切开逐段翻译。
4. 一个 `MutationObserver` 监视整个页面：**应用之后写进页面的文字和属性**（`placeholder`、`title`、`aria-label`、`alt`）也会被自动翻译；每个文本节点会记住自己的中文原文，切换语言时从原文重新翻译，所以来回切换不会累积错误。
5. 带 HTML 标签的整段说明（里面有 `<code>`）用 `data-i18n-html` 标记，整段作为词典键，避免“按片段翻译”造成语序错乱（日语、韩语语序与中文差别大）。
6. `window.confirm()` 也被包了一层。
7. 语言选择存在 `localStorage`，默认跟随浏览器语言，没有对应语言时用英语。

**为什么不用现成的 i18n 库？** 因为页面要**零依赖**、可离线、一个文件。词典法对这个规模（约 300 条）最简单。仓库里有测试 `tests/test_ui_i18n.py`，检查每行都是 5 列、占位符个数在各语言里一致、没有重复的源字符串，以及页面里所有中文文本节点都有译文。

### 7.4 端口与跨域

网页由 `8765` 提供，绘制服务在 `8770`，所以浏览器是**跨端口请求**。绘制服务返回 CORS 头；预览图要带 `crossOrigin="anonymous"`，否则 `<canvas>` 会被“污染”，读取像素时抛 `SecurityError`。页面轮询频率：游戏状态约 1 秒、画布约 1.8 秒（绘制中 0.8 秒）、活动作业 0.6–0.8 秒、作业列表 8 秒。

| `tools/probe_pen.py` | 虚拟笔是否被游戏接受；测游戏帧率 |

## 9. 安全、隐私与公平游戏

- **只在本机**：桥接（8765）与绘制服务（8770）都只绑定 `127.0.0.1`。设置了 `Token` 后，API 请求必须携带。**不要把端口暴露到网络。**
- **图片不出本机**：图片只在本机处理，不上传到任何服务器。安装时联网下载的只有 BepInEx 和（可选的）两个模型文件，**全部校验 SHA-256**。
- **不分发游戏文件**：插件在用户机器上对本机游戏程序集编译。
- **进程隔离**：Python 服务是独立子进程，崩溃不会拖垮游戏；插件按配置启停它，并提供 `/shutdown`。
- **公平游戏**：Sumie 面向单人 Sketchbook、征得同意的私人房间、实验与学习。**请不要用它在公开对局中获取不正当优势或干扰其他玩家**；遵守游戏的服务条款是使用者自己的责任。让画面“像手绘”是为了观感，**不是为了伪装身份或绕过检测**。

## 10. 从零复现指南（八步）

下面这份指南让你**不看源码**也能做出一个最小可用的等价系统。每一步都能单独验证。

### 第 1 步：准备环境

- 游戏：Steam 上的 Draw & Guess，**Mono 版**。
- 工具：Python ≥ 3.10、.NET SDK ≥ 6、git。
- 找到游戏目录（macOS 例：`~/Library/Application Support/Steam/steamapps/common/Draw & Guess`，Windows 例：`C:\Program Files (x86)\Steam\steamapps\common\Draw & Guess`）。
- 装 BepInEx 6（`Unity.Mono` 版，仓库固定 build 790），并校验 SHA-256。macOS 需要用 `run_bepinex.sh` 作为 Steam 启动项，Windows 是 `winhttp.dll` 代理自动加载。**你可以直接运行 `tools/install.py --check` 看它找到什么。**

### 第 2 步：写一个最小插件（能收到 HTTP 请求）

1. 新建 `netstandard2.1` 类库，引用 `BepInEx.Core`、`BepInEx.Unity.Mono`、`0Harmony`、游戏的 `UnityEngine*.dll` 与 `Assembly-CSharp.dll`（`Private=false`）。
2. 写一个继承 `BaseUnityPlugin` 的类（见 2.1）。
3. 在 `Awake()` 里用 `System.Net.HttpListener` 监听 `http://127.0.0.1:8765/`，在**后台线程**读请求。
4. 实现 2.2 的 `MainThreadDispatcher`，`Update()` 里 `Pump()`。
5. 先实现一个只读端点 `GET /api/v1/state`：把“能不能画”等信息放进 JSON，**用 `Invoke` 等主线程算完再返回**。
6. 编译，把 DLL 复制到 `BepInEx/plugins/`，启动游戏，浏览器访问 `http://127.0.0.1:8765/api/v1/state`。看到 JSON 就成功了。

> 提示：游戏内部类名（如 `DrawHelpers`、`LineInformation`、`DrawModule`）需要你用 dnSpy / ILSpy 反编译 `Assembly-CSharp.dll` 查看；仓库的 `GameApi.cs` 是一份可对照的实现。

### 第 3 步：让插件能画一条线

在 `POST /api/v1/strokes` 里，对每个笔画：按 2.5 的 8 个步骤构造 `LineInformation` 并 `SpawnDrawElement`。**用协程每帧最多处理 24 条。** 先只实现 `line` 和 `disc`。

验证：

```bash
curl -s -X POST http://127.0.0.1:8765/api/v1/strokes \
  -H 'Content-Type: application/json' \
  -d '{"strokes":[{"type":"line","color":"#FF3355","size":10,"points":[[0.1,0.2],[0.25,0.8],[0.5,0.3]]}]}'
```

画布上应当出现一条红色折线。**用 `GET /api/v1/lines` 回读，确认 y 向上（头顶 y 大）。**

### 第 4 步：用 Python 把一张图变成笔画

仓库自带最小演示 `examples/minimal_strokes.py`（只依赖 OpenCV）：

```python
img = cv2.imread(path, cv2.IMREAD_GRAYSCALE)
img = cv2.resize(img, ...)                              # 最长边 480
edges = cv2.Canny(cv2.GaussianBlur(img, (3, 3), 0), 60, 140)
contours, _ = cv2.findContours(edges, cv2.RETR_LIST, cv2.CHAIN_APPROX_NONE)
...
for c in contours:
    c = cv2.approxPolyDP(c, 1.2, False)[:, 0, :]        # 折线简化
    pts = [[x0 + px / w * fit_w, y0 + (1 - py / h) * fit_h] for px, py in c]   # 2.3 的换算
    strokes.append({"type": "line", "color": "#202020", "size": 4, "points": pts})
```

运行：

```bash
python examples/minimal_strokes.py examples/sample.png > strokes.json
python client/dg_bridge.py draw-json strokes.json
```

到这里你已经有了一个“能把边缘画上去”的版本。接下来每一步都在**提高画得像不像人、像不像原图**。

### 第 5 步：换成更好的线稿和调色板

- 用 Anime2Sketch 替换 Canny（3.3）。权重 `netG.pth` 可由 `python tools/setup.py --ai` 下载并校验。
- 做骨架化 + 接线 + 断线（3.3 的 2–4），得到少而长的笔画。
- Lab k-means 取 3–8 种颜色，对每个色块生成**简单多边形**，用 `fill` 发送（3.4）；**不要发自交多边形。**

### 第 6 步：加上压感和节奏

1. 把 5.1.2 的 `game_brush_size` 抄过去（它是纯函数，可以单测）。
2. 给每笔选一个目标 `size`，反推压力 `p ≈ (size − 2) / 33`，生成逐帧压力序列（保证每帧 > 0.05，前 70 ms 不动）。
3. 用 5.2 的幂律生成每笔时长和笔间停顿；用 20 段速度剖面沿路径分配时间。
4. 先用 `direct` 模式（一笔一个 `POST /strokes`，笔间 `sleep`）。
5. 再在插件里实现 `POST /stroke/pen`：创建虚拟 `Pen`，按采样逐帧 `InputSystem.QueueStateEvent`，结束时压力归零再等几帧。**需要游戏设置里的压感打开，否则返回 409。**

### 第 7 步：加上时间预算

照 6.1：在读图**之前**记录 `planning_start`，算出 `deadline`；执行循环里每一笔都检查，并按 6.2 的压缩比调整节奏；时间不够就从清单末尾丢笔画。

### 第 8 步：加上图层与漏色模型（高级）

- 插件里实现虚拟图层（5.4.2），暴露 `GET /api/v1/layers`，让 `POST /strokes` 接受 `vlayer`。
- Python 里实现 `brush_fill`（5.4.4）：色块可涂范围、来回扫、中轴线、覆盖率目标。
- 需要油漆桶时，实现离线桶模型（5.5）并在执行时比对实际面积。

### 复现时最容易踩的坑

| 坑 | 症状 | 解法 |
|---|---|---|
| 在非主线程碰 Unity 对象 | 随机崩溃 / 报错 | 一律通过调度器 |
| 把 y 当成向下 | 画面上下颠倒 | 统一 y 向上，只在画到图片时翻转 |
| 压力 ≤ 0.05 的帧 | 一笔被拆成两笔 / 线被截断 | 每帧压力 > 0.05，起笔先停 70 ms |
| 发自交多边形 | 出现大块深色 | 规划时丢弃自交多边形 |
| 预览与实际线宽公式不一致 | 预览比实际粗 | 全部用 2.4 的公式 |
| 倒桶后颜色被下一笔改掉 | 全图填充变成同一个颜色 | 插件里关掉“可选中”；执行器倒完切回画笔 |
| 倒桶种子取色块中心 | 倒不出东西 | 取格子里最深的点，备用点兜底 |
| 规划耗时没算进截止时间 | 画到回合结束还没画完 | 截止时间从读图之前开始算 |

## 12. 常见问题

**Q：这会被检测到吗？**
A：Sumie 不隐藏自己，也不是为了对抗检测设计的。笔迹“像手绘”只是为了好看、过程自然。请遵守游戏的服务条款，并只在合适的场合使用（见第 9 章）。

**Q：为什么我的画和原图不太像？**
A：时间越短，笔画越少、越简化。试试把秒数调到 180–300，或安装 AI 模型（`--ai`）。先看“预览”里的覆盖率和颜色误差。

**Q：为什么一定要 Mono 版？**
A：BepInEx 6 的 Unity.Mono 加载器只支持 Mono 运行时的游戏。IL2CPP 版需要另一套（Il2Cpp）加载器，本项目没有适配，安装器会拒绝。

**Q：游戏更新后插件坏了怎么办？**
A：重新运行安装器；如果游戏内部类改名 / 改签名，需要改 `GameApi.cs`。

**Q：为什么 Python 服务是独立进程，不直接放进插件？**
A：游戏里只能跑 .NET 代码，OpenCV / PyTorch 的生态在 Python；而且规划很耗 CPU，放到独立进程里不会卡住游戏画面，崩溃也不会拖垮游戏。

**Q：我能自己加一种画风吗？**
A：能。在 `dg_artist.py` 里注册新的风格函数，产出 Op 列表即可；执行器、预览、指标、网页都复用。

## 13. 已知限制与路线图

**限制**

- 调色按封闭区域的中值，柔和的渐变会成平色；阴影靠圈出的暗部补一点；
- 极细的补口线（压力接近 0.05 的下限）在游戏里不易看见，但会挡住油漆桶；
- 游戏大版本更新可能改变内部类，插件需要相应调整；
- 虚拟图层在别的玩家客户端上的显示，最好在私人房间用第二台电脑确认；
- 仅支持 Mono 版游戏；
- 界面多语言覆盖网页工作台，命令行输出与 `docs/` 技术文档仍以中文为主。

**路线图**

- 更多风格、更细的阴影模型；
- Windows / Linux 上更多真机验证；
- 把 `docs/` 的其余技术文档翻译成英文；
- 用 WebSocket 推送进度，替代轮询。

## 14. 术语表

| 术语 | 白话解释 |
|---|---|
| **插件（Plugin）** | 装进别的程序里、给它增加功能的小程序 |
| **BepInEx** | 给 Unity 游戏加载插件的开源工具 |
| **Mono / IL2CPP** | Unity 游戏的两种“运行方式”；Mono 能被 BepInEx 6 直接加载 |
| **主线程** | 游戏里唯一能操作游戏对象的“柜员” |
| **HTTP / WebSocket** | 程序之间说话的两种方式：一问一答 / 一直开着线路 |
| **127.0.0.1** | “本机地址”，只有你自己的电脑能访问 |
| **API** | 程序之间约定好的“点菜单” |
| **位图 / 矢量** | 由像素点组成的图 / 由线条和坐标描述的图 |
| **线稿** | 只有轮廓线的黑白图 |
| **骨架化** | 把粗线“瘦”成一条中心线 |
| **k-means** | 把相近的数据自动分成 k 组的算法，这里用来找主要颜色 |
| **Lab 色彩空间** | 数值距离接近人眼颜色差别的色彩表示 |
| **GrabCut** | OpenCV 里经典的前景提取算法 |
| **ONNX** | 跨框架的神经网络文件格式 |
| **U-Net / ISNet** | 两种常用于图像到图像任务的神经网络结构 |
| **压感** | 数位板感知按压力度，力度大线条粗 |
| **图层** | 叠在一起的透明层；高层盖住低层 |
| **SortingOrder** | Unity 里决定谁盖住谁的数值 |
| **油漆桶** | 点一下填满封闭区域的工具 |
| **归一化坐标** | 把宽高都缩放到 0–1 之间的坐标 |
| **幂律** | 形如 `y = a·x^b` 的关系 |
| **对数正态** | 取对数后呈正态（钟形）分布的随机量，适合描述“总是正数、偶尔很大”的量 |
| **LPIPS** | 用神经网络衡量两张图“看起来像不像”的数值，越小越像 |
| **CORS** | 浏览器对“跨网址 / 跨端口请求”的安全规则 |
| **确定性** | 输入相同输出必然相同 |
| **Harmony** | 在运行时给 .NET 方法“打补丁”的库 |
